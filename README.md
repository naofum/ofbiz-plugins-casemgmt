# ofbiz-plugins-casemgmt

Apache OFBiz 上でケース管理を行うためのプラグインです。

「問い合わせ」「申請」「契約」「社員の入社手続き」のように、複数の人・複数の処理・判断・待ちをまたぐ業務を、**1つのケースとして発生から完了まで管理**できます。

- 要件・仕様: `SPEC_CASEMGMT_OFBIZ.md`
- Web UI: `/casemgmt/control/main`

---

## 1. ケース管理とは

### 1.1 「ケース」は1件の業務の流れをまとめたものです

たとえば、顧客から苦情が届いたとします。

1. 受付担当が内容を確認する
2. 担当部署を決める
3. 調査する
4. 上長が対応方針を承認する
5. 顧客へ回答する
6. 完了を確認してクローズする

この一連の流れを、1つの「ケース」として扱います。

ケースには次の情報がまとまります。

- 現在どの段階にいるか
- 誰が担当しているか
- 次に何をすべきか
- 期限はいつか
- どのような判断・差し戻しがあったか
- どの業務データ（顧客、契約、申請など）と関係しているか

### 1.2 なぜケース管理が必要なのか

業務は、単純な1回の登録で終わらないことが少なくありません。

- 複数人で分担する
- 途中で判断や承認が必要になる
- 顧客や外部システムの返答を待つ
- 差し戻しや再作業が発生する
- 期限や優先順位を守る必要がある

ケース管理がないと、次のような問題が起きます。

- 誰が何をすべきか分からず、案件が止まる
- メールや表計算に情報が散らばり、抜け漏れが起きる
- 担当者の記憶や個人の進め方に依存する
- 滞留している案件が見えない
- 過去の判断理由を説明できない
- 顧客への対応品質が担当者によってばらつく

ケース管理では、**案件の状態・担当・期限・履歴・関連データを1か所で管理**します。これにより、抜け漏れ防止、進捗の可視化、属人化の解消、監査対応、継続的な業務改善がしやすくなります。

### 1.3 ワークフローエンジンとの違い

このプラグインは、BPMN を完全に実行する汎用ワークフローエンジンではありません。

- ケース全体の進行、担当、期限、状態、履歴を管理する
- 実際の業務処理は OFBiz のサービスや業務エンティティに任せる
- フォームや画面は OFBiz の仕組みを再利用する

「案件を進めるための管理台帳と進行エンジン」と考えると分かりやすいです。

## 2. Apache OFBiz でケース管理を行うメリット

### 2.1 既存の業務データをそのまま使える

OFBiz には、次のような業務データが最初から用意されています。

- 取引先・個人・グループ（Party）
- 商品・カタログ
- 見積・注文
- 契約・請求
- 人事・組織
- WorkEffort（作業・タスク）

ケース管理のために別システムへデータをコピーするのではなく、**既存の OFBiz データとケースを直接リンク**できます。

### 2.2 OFBiz の基盤機能を再利用できる

ケース管理を独自システムとして作ると、次の機能を別途用意する必要があります。

- ログイン・認証
- ユーザー・権限管理
- サービス呼び出し
- トランザクション管理
- スケジュールジョブ
- フォーム・画面
- 帳票・CSV
- 監査ログ

OFBiz 上に実装することで、これらを既存の仕組みとして活用できます。

### 2.3 二重管理を避けられる

顧客情報や契約情報をケース側にコピーすると、元データとケース側のデータが食い違う可能性があります。

このプラグインでは、ケースは業務データの「正」を持たず、`CaseContext` で業務エンティティを参照します。業務データの更新は OFBiz の既存サービスに任せられます。

### 2.4 クラスタ運用を考慮できる

タスク完了、ケース遷移、SLA 更新、外部シグナルなどは、条件付き更新や楽観ロックを使って二重処理を防ぎます。複数の OFBiz サーバーで運用する場合でも、同じ DB を共有することで整合性を保ちやすくしています。

## 3. このプラグインの特徴

### 3.1 ケース管理カーネルと業務別プラグインを分離

ケース管理の基本機能は `plugins/casemgmt` にまとめています。

人事・与信・ローンなど、特定業務のフォームやサービスは、将来的に次のような業務別プラグインへ分離できます。

- `plugins/casemgmt-humanres`
- `plugins/casemgmt-finance`

ケース管理カーネルが特定業務に依存しないため、業務ごとに画面やサービスを追加しやすくなります。

### 3.2 OFBiz の標準フォームを再利用できる

OFBiz の標準フォームをそのままケース画面に埋め込むのではなく、次の方法でケース専用フォームを作ります。

- 標準フォームを `extends` して target だけケース用に変更する
- `auto-fields-service` でケース専用フォームを作る
- 標準フォームの項目を参考に、統合プラグイン側でフォームを定義する

開始フォームとタスクフォームはメタデータで指定し、送信先が `StartCaseSubmit` / `TaskFormSubmit` であることを検証します。標準フォームの target を直接呼び出さないことで、ケースの権限・トランザクション・履歴を一貫して扱えます。

### 3.3 ケースと業務データを `CaseContext` で接続

ケースと業務エンティティをリンクします。

- 単一主キー
- 複合主キー
- 主業務エンティティと関連エンティティの区別
- 開始フォームで作成した業務エンティティの自動リンク

例:

```text
Case（苦情ケース）
  ├─ CaseContext → Party（顧客）
  ├─ CaseContext → Order（注文）
  └─ CaseContext → Product（対象商品）
```

### 3.4 メタデータでケースの流れを定義

ケースタイプ、ステージ、ステップ、遷移、フォーム、SLA、割当をメタデータとして管理します。

- 定義はバージョン単位で固定
- 稼働中のケースは作成時の定義バージョンで実行
- ドラフト作成、検証、公開、複製、差分確認、退役
- ステージ・ステップ・遷移の並び替え

### 3.5 `WorkEffort` を基盤にしている

ケースのルートは `WorkEffort` です。

```text
WorkEffort (workEffortTypeId = CASE)
  └─ Case (1:1 拡張)
       ├─ CaseTask
       ├─ CaseStageInstance
       ├─ CaseEvent
       ├─ CaseVariable
       └─ CaseContext
```

人間タスクは `CASE_ASSIGNMENT` の子 `WorkEffort` と `CaseTask` を組み合わせて管理します。OFBiz の作業・タスクの仕組みと連携しつつ、ケース固有の状態や履歴を追加しています。

## 4. 基本概念

| 用語 | 意味 |
|---|---|
| ケースタイプ（CaseType） | 業務の種類。「苦情対応」「与信申請」「入社手続き」など |
| ケース（Case） | 実際に発生した1件の案件 |
| ステージ（Stage） | ケースの大きな段階。「受付」「調査」「承認」「完了」など |
| ステップ（Step） | ステージ内の具体的な作業単位 |
| 遷移（Transition） | ステップ完了後に次へ進む条件と行き先 |
| アウトカム（Outcome） | 完了・承認・却下・差し戻しなどの結果 |
| ケースタスク（CaseTask） | 人またはサービスが実行する作業 |
| キュー（Queue） | グループで案件を分担するための待ち行列 |
| SLA | 対応期限・解決期限などのサービスレベル |
| 開始フォーム | ケースを作る前に業務情報を入力するフォーム |
| タスクフォーム | タスクを完了するときに表示するフォーム |
| `CaseContext` | ケースと業務エンティティのリンク |
| `CaseVariable` | ケース実行中だけ保持する短期変数 |
| プロセスマップ | ケースの流れを図で確認する機能 |

## 5. ケースの作り方と使い方

### 5.1 管理者: ケースタイプを定義する

1. `/casemgmt/control/CaseTypeList` を開く
2. ケースタイプのドラフトを作成する
3. ステージを追加する
4. 各ステージにステップを追加する
5. ステップ間の遷移とアウトカムを設定する
6. 必要に応じて開始フォーム・タスクフォームを設定する
7. サービスステップの入力・出力マッピングを設定する
8. 定義を検証する
9. 問題がなければ公開する

定義は次の状態を持ちます。

- ドラフト: 編集中
- 公開: 新しいケースで利用可能
- 退役: 新規利用を停止

既存の公開定義を変更する場合は、ドラフト版を作成し、差分を確認してから公開します。

### 5.2 利用者: ケースを開始する

1. メイン画面またはケースワークリストを開く
2. 「ケースを作成」を選ぶ
3. ケースタイプを選ぶ
4. 開始フォームが定義されていれば、業務情報を入力する
5. フォーム送信後にケースが作成される

開始フォームが未定義の場合は、従来の簡易フォームでケースを作成できます。

```text
ケースタイプ選択
  → 開始フォーム
  → 開始サービス（業務エンティティ作成）
  → ケース作成
  → CaseContext リンク
  → ケース詳細
```

### 5.3 利用者: タスクを進める

1. メイン画面で自分に割り当てられたケースを確認する
2. ケース詳細を開く
3. タスクを開く
4. タスクフォームまたは動的フォームを入力する
5. 完了ボタンを押す
6. 遷移条件に従って次のステップへ進む

タスクフォームが定義されている場合は、フォーム送信とタスク完了を同一トランザクションで実行します。フォームがない場合は、動的フォーム、または単純な完了画面を使用します。

### 5.4 メインとケースワークリストの違い

| 画面 | 用途 |
|---|---|
| メイン | 自分に割り当てられたケースを確認する |
| ケースワークリスト | 権限内の全ケースを条件検索する |

ケースワークリストでは、次の条件で検索できます。

- ケースタイプ
- ステータス
- ステージ
- キュー
- 担当者
- SLA 状態
- SLA マイルストーン
- 滞留期間
- 作成日
- クローズ済の表示期間（非表示 / 過去1週間 / 過去1か月 / 過去1年）

ケース滞留分析やレポートの集計行をクリックすると、その条件を引き継いだケースワークリストへ移動できます。

## 6. 各機能の説明

### 6.1 ケースタイプ管理

ケースタイプは、業務のテンプレートです。

- ステージ、ステップ、遷移を定義
- ステップ種別ごとに必要な項目を設定
- 開始フォーム、タスクフォームを定義
- サービス入出力、SLA、割当ポリシーを設定
- バージョン複製、差分、検証、公開、退役
- ドラフト削除時に配下の定義も削除

### 6.2 ステージ

ステージはケースの大きな区切りです。

例:

```text
受付 → 調査 → 承認 → 完了
```

設定できる主な項目:

- ステージ名
- ステージ種別
- 自動進行するか
- 入口条件サービス
- 出口条件サービス
- 説明

### 6.3 ステップ

ステップは、ステージ内で実際に行う作業です。

| ステップ種別 | 用途 | 例 |
|---|---|---|
| Human Task | 人がフォームや画面で作業する | 内容確認、承認、電話対応 |
| Service | OFBiz のサービスを自動実行する | 与信チェック、在庫確認、通知 |
| Decision | 条件を評価して分岐する | 金額や与信結果によるルート分岐 |
| Wait | 外部シグナルや時間経過を待つ | 顧客回答待ち、外部システム連携待ち |
| Sub-case | 子ケースを開始する | 調査ケース、審査ケース |

#### Wait ステップ

Wait ステップでは、ステップ作成・編集画面で次を設定できます。

- シグナル名（`signalName`）
- タイムアウト（分）
- タイムアウト時のアウトカム

外部から `signalCaseTask` を呼ぶときは、設定したシグナル名と一致する `signalName` を渡します。`idempotencyKey` は必須です。シグナル名が設定されていない Wait は、任意のシグナルで完了できます。

タイムアウトを設定した場合、`processCaseWaitTimeouts` が1分間隔で期限切れの Wait タスクを検出し、設定したアウトカムで完了させます。タスク完了とケース遷移は同一トランザクションで処理され、条件付き更新により二重処理を防ぎます。

#### Sub-case ステップ

Sub-case ステップでは、ステップ単位で子ケースタイプ（`subCaseTypeId`）を指定できます。複数の Sub-case ステップに異なる子ケースタイプを設定できます。

既存データとの互換性のため、ステップに子ケースタイプがない場合は、ケースタイプ属性 `SUB_CASE_TYPE` がフォールバックとして使われます。

### 6.4 遷移

遷移は「このステップがこの結果で終わったら、次はどこへ行くか」を定義します。

設定できる主な項目:

- アウトカム（完了、承認、却下、差し戻しなど）
- 遷移先ステージ・ステップ
- 条件サービス
- 優先順位
- デフォルト遷移かどうか

条件サービスを使うと、同じアウトカムでも条件によって別のステップへ分岐できます。差し戻しも遷移として表現できます。

```text
承認ステップ
  ├─ APPROVE → 完了ステップ
  ├─ REJECT  → 修正ステップ
  └─ COMPLETE（デフォルト）→ 完了ステップ
```

### 6.5 開始フォームとタスクフォーム

開始フォームは、ケース作成前に業務情報を入力する画面です。タスクフォームは、タスク完了時に表示する画面です。

メタデータで指定するもの:

- フォームの配置（`formLocation`）
- フォーム名（`formName`）
- 送信先（`formTarget`）
- 開始サービス名
- タスク完了サービス名
- 説明

フォームの target は、開始フォームなら `StartCaseSubmit`、タスクフォームなら `TaskFormSubmit` であることを保存時に検証します。

#### 標準フォーム再利用の PoC

`CasemgmtForms.xml` の `CaseStandardPartyNoteForm` は、OFBiz 標準の `AddPartyNote` フォーム（`component://party/widget/partymgr/PartyForms.xml`）を `extends` し、送信先だけを `TaskFormSubmit` に変更した例です。

- 標準フォームの項目や `auto-fields-service` はそのまま再利用
- 標準フォーム自体は変更しない
- 完了サービスには標準の `createPartyNote` を指定
- テスト用ケースタイプ `TEST_STANDARD_FORM` で、フォーム表示からタスク完了・標準サービス実行までを確認

業務別プラグインでも、標準フォームを `extends` したアダプターと、業務サービスを組み合わせることで同じ方式を利用できます。

### 6.6 動的フォーム

フォーム定義を作らずに、項目をメタデータで定義する方法もあります。

- 項目名
- ラベル
- 入力種別（テキスト、数値、日付、チェックボックス、ドロップダウン、参照）
- 必須かどうか
- 表示条件サービス
- 読み取り専用条件サービス
- 保存先エンティティ・項目
- ロケール別ラベル（`CaseFieldLabel`）

ロケール別ラベルには `ja`、`ja_JP`、`en` のようなロケールを指定します。表示時は、完全一致するロケール、言語だけのロケール、`CaseFieldMapping.label`、項目名の順にフォールバックします。管理画面の「ケースタイプ編集 → 項目編集」から、ロケール別ラベルを追加・更新・削除できます。

タスクフォームがない場合は、この動的フォームが使われます。

### 6.7 サービスステップの入力・出力マッピング

Service / Decision ステップでは、サービスの入力をメタデータでマッピングできます。

入力元の例:

- 固定値
- 実行コンテキスト（`caseId` など）
- ケース項目
- ケース変数
- `CaseContext` でリンクした業務エンティティの項目

出力は、`CaseStepServiceOutput` で宣言した項目だけを `CaseVariable` に保存します。

```text
サービスの出力
  approvedAmount = 500000
  approved = true
        ↓ 宣言した項目だけ保存
CaseVariable
  credit.limit = 500000
  credit.approved = true
```

複雑な値は JSON として保存できます。機密フラグ、スコープ、TTL も保持します。

> 補足: TTL の期限切れ自動削除は今後の拡張対象です。現時点では、ケースクローズ時に実行時変数を削除します。

### 6.8 ケースと業務データのリンク

`CaseContext` で、ケースと業務エンティティをリンクします。

- 単一主キーのエンティティ
- 複合主キーのエンティティ
- 複数の関連エンティティ
- 主業務エンティティと関連エンティティの区別

開始フォームの開始サービスが `businessEntityName` と `businessKeys` を返すと、ケース作成後に自動でリンクされます。

### 6.9 ケース変数

`CaseVariable` は、ケース実行中だけ利用する短期変数です。

- サービス出力を次のステップへ渡す
- Decision の条件判定に使う
- 複雑な結果を JSON で保持する
- 機密値にフラグを付ける
- スコープと TTL を設定する

ケースをクローズすると、実行時変数を削除します。

### 6.10 割当とキュー

タスクは次の方法で担当者を決められます。

- 特定の担当者に固定
- ラウンドロビン
- 最小負荷
- スキルベース
- キューピック
- 手動 claim / reassign / release

グループ運用はキュー方式です。ステージ単位のオーナーは設けず、ケース全体のオーナーとキューの担当者で運用します。

### 6.11 権限とアクセス制御

OFBiz のユーザー・セキュリティグループを利用します。

- `CASEMGMT_USER`: 一般的なケース利用者
- `CASEMGMT_ADMIN`: ケース管理の管理者
- `CASEMGMT_VIEW` / `CASEMGMT_CREATE` / `CASEMGMT_UPDATE` / `CASEMGMT_ADMIN` / `CASEMGMT_CASE_TYPE_EDIT`

ケースごとのアクセスポリシーやルールも設定でき、参照・更新できるユーザーを制限できます。

### 6.12 SLA

SLA は、対応期限や解決期限を管理する機能です。

- SLA マイルストーンを定義
- ケース作成時に SLA インスタンスを生成
- 目標日時、期限日時、期限超過日時を計算
- JobSandbox のジョブで定期監視
- 状態変更、違反、エスカレーションを記録
- 条件付き更新で二重更新・二重エスカレーションを防止

### 6.13 プロセスマップ

ケース詳細とケースタイプ編集画面で、Mermaid のプロセスマップを表示します。

ケースタイプ編集画面では次の3種類を表示します。

1. ステージ図
2. ステップ順序図
3. 条件分岐付き遷移図

遷移図には、アウトカム、デフォルト遷移、条件サービスを表示します。

### 6.14 レポートと滞留分析

次の情報を集計できます。

- サイクルタイム
- SLA 遵守率
- バックログ
- ステージ別・キュー別・担当者別の滞留
- スループット
- 再作業
- 自動進行率

レポートは CSV でエクスポートできます。集計行から条件付きケースワークリストへ遷移できます。

### 6.15 同時実行制御と冪等性

複数サーバーで運用しても二重処理が起きないようにしています。

- タスク完了・claim・release・シグナルは状態条件付き更新
- ケース遷移は `Case.version` による楽観ロック
- SLA 状態・完了・エスカレーションは条件付き更新
- 外部シグナルは `idempotencyKey` で再送を判定
- `CaseEvent.idempotencyKey` に一意制約
- Wait のタイムアウト完了も状態条件付き更新で保護
- 複数の子ケースが同時に完了しても、親ケースのロックと親タスクのCAS更新で二重遷移を防止

### 6.16 デバッグ用サービス

開発・運用時の調査用に、次のサービスを用意しています。

- `caseDebugLogMessage`: 指定文字列をログ出力
- `caseDebugLogServiceParameters`: サービス入出力と `CaseVariable` をログ出力
- `caseDebugInvokeService`: 対象サービスを実行し、入出力とケース変数をログ出力

機密値はデフォルトでマスクされます。パラメータログと実行ラッパーは `CASEMGMT_ADMIN` 権限が必要です。

## 7. 典型的な利用例

### 7.1 顧客苦情

```text
受付
  → 内容確認
  → 調査
  → 対応方針承認
  → 顧客回答
  → 完了
```

- 開始フォームで顧客・対象商品・苦情内容を入力
- `CaseContext` で顧客や注文をリンク
- 調査タスクと承認タスクを Human Task で管理
- SLA で初回応答と解決期限を監視
- 却下・差し戻しは遷移で表現

### 7.2 サービス要求

```text
受付
  → 影響範囲確認
  → 承認
  → サービス実行
  → 完了確認
```

- サービスステップで OFBiz の業務サービスを実行
- 実行結果を `CaseVariable` に保存
- 次ステップの判断材料として利用

### 7.3 新入社員オンボーディング

```text
入社情報入力
  → 社員登録
  → 研修
  → PC 支給
  → アカウント発行
  → 完了
```

- 人事系の標準フォームや標準サービスを統合プラグイン側でラップ
- 複数の業務タスクを1つのケースで進捗管理

業務別プラグイン `plugins/casemgmt-humanres` に、`ONBOARDING` ケースタイプの最小実装があります。

```text
入社情報入力
  → 社員登録
  → 初回研修
  → 設備割当
  → アカウント発行
  → 完了確認
```

- 開始フォームで従業員の `Person` とメールアドレスを作成
- 社員登録タスクで `Employment`、上長関係、職種を登録
- 上長は標準の `LookupPartyName`（パーティ検索）から選択
- 研修・設備・アカウントの各タスクで標準エンティティ／標準サービスへ連携
- キュー `ONBOARDING_QUEUE`、SLA `ONBOARDING_SLA` を標準データとして提供

既存DBへオンボーディング定義を追加する場合は、OFBiz を停止してから次を実行し、再起動してください。

```text
gradlew.bat "ofbiz --load-data readers=seed --load-data component=casemgmt-humanres"
```

デモ用の部署 `DEMO_HR_DEPT`、上長 `DEMO_HR_MANAGER`、キュー担当 `admin` も同時に投入する場合は、`readers=seed,demo` を指定します。

```text
gradlew.bat "ofbiz --load-data readers=seed,demo --load-data component=casemgmt-humanres"
```

詳細は `plugins/casemgmt-humanres/README.md` を参照してください。

## 9. 管理者向け設定

### 9.1 権限

ケース管理画面を利用するには、`CASEMGMT_USER` または `CASEMGMT_ADMIN` のセキュリティグループに所属する必要があります。

シードデータでは、標準の `admin` ユーザーが利用できるように `FULLADMIN` へ `CASEMGMT_*` 権限を付与しています。運用環境では、必要なユーザーだけに権限を付与してください。

### 9.2 初期データ

ケースタイプのサンプルや Enum、SLA、キュー、権限は、OFBiz の seed データとして投入されます。

## 11. 設計上の注意

- BPMN 2.0 の完全な実行エンジンではありません
- 任意のスクリプトをケース定義から実行する仕組みではありません
- 人事・与信・ローンなど業務固有の処理は、業務別プラグインへ分離する方針です
- 標準フォームを直接 target 呼び出しせず、ケース専用フォーム経由で実行します
- Service 入力の `FORM_VALUE` は未対応です
- `CaseVariable` の TTL 期限切れ自動削除は今後の拡張対象です
- ステージ単位のオーナーは設けず、キューとケース全体のオーナーで運用します
